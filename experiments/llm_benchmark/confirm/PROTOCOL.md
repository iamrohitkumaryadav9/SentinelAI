# Phase 1B confirmatory experiment: pre-registered protocol

**Status: pre-registered.** This file, `protocol.json`, `scenarios.json` and the code were committed **before either model ran**. Nothing below may change after results are seen. Any deviation is reported as such in the evaluation.

## Question

Does the observed difference between **qwen3:8b** and **qwen3.5:9b** survive a larger and more targeted agent evaluation?

## Fixed configuration (identical for both models)

| Item | Value |
|---|---|
| Models | qwen3:8b (`500a1f06…`), qwen3.5:9b (`6488c96f…`). The runner refuses any other model. |
| Run order | qwen3:8b, then qwen3.5:9b (one resident model; the other is unloaded) |
| Decoding | `temperature=0`, `seed=42`, `num_ctx=4096`, `num_predict=320` per turn, `think=false` (the run aborts if the Phase 1B probe disagrees) |
| Harness | Phase 1B `benchmark.chat` / `Sampler` / warm-up, unchanged. Measurement-only addition: maximum swap used. |
| Tools | `schemas/tools.json`, unchanged (5 tools) |
| Step budget | At most 6 tool calls per scenario. A 7th call means `step_budget_exhausted` (non-termination). No forced-conclusion turn, exactly as in Phase 1B. |
| Ollama | Unchanged: 0.35.0 with the `LLAMA_ARG_CACHE_RAM=0` drop-in. Swap and zram unchanged (as found). |
| Safety | Per-turn timeout of 300 s; abort if `MemAvailable` falls below 2 GiB. No early stopping on quality grounds; all 48 scenarios run for both models. |

### Differences from the Phase 1B agent suite (identical for both models)

1. **The system prompt gives explicit label definitions**, including the TCP-retransmission versus packet-loss rule. It also adds the label `application_bottleneck` and requires a structured final answer (`DIAGNOSIS` / `CONFIDENCE` / `EVIDENCE`). Without definitions the gold labels would be a convention the models could not know.
2. **Tools respect their arguments** (`simulator.py`). An unknown host, interface, service or CPU returns an explicit error. Interface, CPU, percentile, log-level and log-limit filters are honoured, and unavailable data returns an error. Window arguments are echoed but do not change values (limitation).
3. **48 new scenarios.** None of the 12 Phase 1B scenarios is reused.

Absolute numbers are therefore **not comparable** with the Phase 1B agent suite. Only the paired comparison between the two models is the object of this experiment.

## Dataset (`scenarios.json`, generated by `scenario_gen.py`)

| Category | n | Content |
|---|---|---|
| A: TCP retransmission vs packet loss | 18 | Sub-cases 1 (retransmissions high, no drops; 3), 2 (drops high, retransmissions low; 2), 3 (both high; 2), 4 (neither high; 2), 5 (insufficient; 2), 6 (congestion; 3), 7 (kernel-proven loss; 2), 8 (cannot distinguish; 2) |
| B: CPU scheduling and throttling | 7 | Run-queue contention, pinned-CPU hotspot, context-switch storm, hypervisor steal, 3 × cgroup throttling |
| C: Network / softirq overload | 6 | Single-queue NET_RX, IRQ affinity, NAPI at 2 Mpps, small-packet flood, softirq **with** drops (rule says packet loss), weak softirq signal |
| D: Memory pressure | 5 | Reclaim, swapping, OOM kills, allocation stalls, page-cache distractor (true cause: CPU) |
| E: Application bottleneck | 5 | DB pool, lock contention, slow dependency, worker pool (CPU-92 % distractor), work-queue full |
| F: Insufficient / ambiguous | 7 | All normal, data missing, weak or conflicting, outside retention, logs-only, several moderate deviations, drops on an irrelevant interface |

**Gold labels:** 13 `INSUFFICIENT_EVIDENCE` (27 %), 6 `tcp_retransmissions`, 7 `network_packet_loss`, 6 `application_bottleneck`, 5 `cpu_contention`, 3 `cpu_throttling`, 4 `softirq_overload`, 4 `memory_pressure`. Distractor evidence appears in 21 scenarios.

**Gold-label validation.** `scenario_gen.validate()` checks every scenario's telemetry against machine-checkable versions of the label definitions, and the dataset is not written if any check fails. Negative tests showed that mutating gold labels (A01, A09, A17, F07, E04, D05, C05) is rejected.

## Per-scenario outcome (exactly one)

| Outcome | Definition |
|---|---|
| `correct` | Label equals gold. For a fault gold label, at least one `required_any` tool was called. For an `INSUFFICIENT_EVIDENCE` gold label, at least one tool was called. |
| `unsupported_diagnosis` | Label equals gold, but the required evidence was never retrieved (or no tool was called at all) |
| `incorrect_diagnosis` | Gold is a fault; the label is a *different* fault |
| `insufficient_evidence_failure` | Gold is `INSUFFICIENT_EVIDENCE`; the model gave a fault label (a guess) |
| `over_cautious` | Gold is a fault; the model answered `INSUFFICIENT_EVIDENCE` |
| `no_diagnosis` | Concluded without a parseable valid label |
| `loop_non_termination` | Step budget exhausted |
| `error` | Request timeout, HTTP error or RAM abort |

**Per-call flags**, reported separately:
- `hallucinated_tool`: tool name not in the schema;
- `invalid_arguments`: strict schema validation fails;
- `unknown_entity_argument`: schema-valid, but the host, interface, service or CPU does not exist;
- `wrong_tool`: `run_experiment` during a production incident, or a scenario concluded without calling any `required_any` tool;
- `evidence_grounded`: for fault gold labels, the `EVIDENCE` line names at least one of the scenario's `diagnostic_terms`.

## Analysis (`analyze.py`)

- Correct rate with Wilson 95 % intervals; multi-step correct rate (correct with 2 or more tool calls); `INSUFFICIENT_EVIDENCE` handling (13 scenarios); per-category accuracy; confusion matrix.
- **TCP boundary:** for gold `tcp_retransmissions`, the number correct, packet-loss false positives, other errors and abstentions. Precision and recall for `tcp_retransmissions` and `network_packet_loss` over all 48 scenarios.
- **Paired comparison:** exact McNemar test (two-sided binomial on discordant pairs), plus a paired bootstrap 95 % CI of the difference in correct rate (10,000 resamples, seed 12345).
- **Performance:**
  - median and p95 scenario latency;
  - median tool calls, median turn latency and turn tokens/s;
  - peak RSS, minimum `MemAvailable`, maximum swap used, mean CPU;
  - quality/s = correct rate ÷ median scenario s; quality/GiB = correct rate ÷ peak RSS GiB;
  - correct diagnoses per minute = n_correct ÷ total wall minutes; correct per GiB = n_correct ÷ peak RSS GiB.
- **No new weighted score is computed.**

## Decision procedure (your hierarchy, thresholds fixed in `protocol.json`)

0. **Adequacy.** A model is adequate if its correct rate is at least 0.70, `insufficient_evidence_failure` is at most 25 % of the 13 ambiguous scenarios, and `loop_non_termination` is at most 10 %. If neither model is adequate, the verdict is **FAIL**.
1. **Rule 1: safety and correctness.** A model is *materially worse* if it has at least 3 more scenarios of `unsupported_diagnosis` or `insufficient_evidence_failure`, or at least 3 more hallucinated-tool or invalid-argument calls, or a **systematic error** the other lacks. A systematic error is one wrong label accounting for at least 3 errors and at least 50 % of a gold class with n ≥ 4. If exactly one model is materially worse on Rule 1, the other is chosen (provided it is adequate).
2. **Rule 2: agent quality.** Overall correct rate, multi-step rate, ambiguous handling and TCP-boundary accuracy are compared. The quality difference counts as **robust** only if the exact McNemar p < 0.05 **and** the bootstrap 95 % CI of the difference excludes 0. If it is robust, the higher-quality model is chosen.
3. **Rule 3: resource efficiency** (used only when Rules 1 and 2 do not decide). A difference is material if median scenario latency differs by at least 20 % or peak RSS by at least 1.0 GiB. If one model is materially better on at least one resource dimension and not materially worse on any, it is chosen, and reported as "quality not robustly different; selected on resource efficiency".
4. **Rule 4: robustness.** If none of the above decides, the result is **NO FINAL PRIMARY: RESULTS TOO CLOSE**. A 1–2 point difference in correct rate never decides on its own.

The verdict and gate are then reported as requested, together with the full raw trade-off table, whichever rule decides.
